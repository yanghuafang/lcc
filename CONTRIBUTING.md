# Contributing to `lcc`

Thanks for your interest in `lcc`, a teaching C compiler built on **flex**, **bison**, and **LLVM 20**. Contributions of all sizes are welcome: bug fixes, new test programs, clearer docs, and language features from the [roadmap](docs/Roadmap.md).

Because `lcc` is primarily a **learning resource**, clarity and small, reviewable changes matter more than large features.

## Ways to contribute

- **Fix a bug** in the lexer, parser, code generator, or debug-info builder.
- **Add a test** that covers a supported language feature (see below).
- **Improve documentation** in `docs/`, or add code comments that explain *why*.
- **Work an item** from the [extension roadmap](docs/Roadmap.md).

## Prerequisites

`lcc` targets **macOS** (Homebrew) and **Ubuntu 24.04 / 26.04**. You need LLVM 20, flex, bison, argparse, graphviz, CMake 3.22+, a C++17 compiler, and a system linker (`clang` or `gcc`).

Install dependencies with the helper scripts:

```bash
cd scripts
./install-deps-macos.sh     # macOS
./install-deps-ubuntu.sh    # Ubuntu 24.04 / 26.04
```

See [docs/Install.md](docs/Install.md) for details and manual CMake options.

## Build

```bash
cd scripts
./build-lcc.sh
```

The binary is written to `../../lcc-build/lcc` (a sibling of the repo, kept out of the source tree).

## Test

Every change must keep the full regression suite green. From `scripts/`:

```bash
./compile-tests.sh && ./link-tests.sh && ./run-tests.sh
```

Each step accepts a single file name so you can iterate quickly:

```bash
./compile-tests.sh 25.quick_sort.c
./link-tests.sh 25.quick_sort.c
./run-tests.sh 25.quick_sort.c
```

`compile-tests.sh` defaults to debug mode (`-g -O0`); pass `--release` for `-O2`.

CI (GitHub Actions) runs the suite on every push and pull request against Ubuntu 24.04 / 26.04 and macOS, plus a debug-info smoke check — run it locally before submitting:

```bash
./check-debug-info.sh          # DWARF present with -g
```

## Adding a test

Test programs live in `tests/` and follow the naming pattern `N.short_name.c`.

1. Create `tests/N.short_name.c`. It should exercise one feature and self-check, printing `N.short_name.c PASS` on success (or `... FAIL`) and returning non-zero on failure. Because there is no preprocessor, declare any libc helpers manually (e.g. `int printf(char*, ...);`) — see [docs/Language.md](docs/Language.md).
2. Register it by adding the file name to the `tests=( … )` array in [`scripts/tests-compile-link-run.sh`](scripts/tests-compile-link-run.sh).
3. Run the suite. Compilation regenerates the golden artifacts under `debug/` (AST `.dot` / `.png` and the `.debug.ll` / `.release.ll` IR). Commit the goldens that correspond to your new test.

Use an existing test such as [`tests/25.quick_sort.c`](tests/25.quick_sort.c) as a template.

## Coding style

- **C++17**, formatted with `clang-format` using the repo's [`.clang-format`](.clang-format) (Google base style, 2-space indent, 80-column limit). Run `clang-format -i` on the files you touch before committing.
- Prefer small, focused changes — **one idea per pull request**.
- Comments should explain **intent and trade-offs**, not restate the code.
- Keep the front-end grammar stable unless the change is specifically a language feature. Grammar edits belong in `Parser.y`; note any new parser conflicts in [docs/Conflicts.md](docs/Conflicts.md) (`Parser.output` is regenerated by the build).

## Commit & pull request

- Write commit messages in the **imperative mood**, capitalized, ending with a period, matching the existing history — e.g. `Zero-initialize file-scope globals with no initializer.`
- Keep unrelated changes out of the same commit, and avoid committing bulk `debug/` diffs your change did not intend to produce.
- Before opening a PR: rebuild, run the full suite and the debug-info smoke check above, and update any affected docs (e.g. [docs/Usage.md](docs/Usage.md) for new CLI flags).
- Describe **what** changed and **why** in the PR, and confirm CI passes on Ubuntu 24.04 / 26.04 and macOS.

## Scope

`lcc` is intentionally a small teaching compiler. Planned extensions and deliberately deferred features (e.g. the preprocessor, 3D arrays, `extern` variables, block-scope `typedef`) are listed in [docs/Roadmap.md](docs/Roadmap.md) — please check there before starting large work, and feel free to open an issue to discuss first.
